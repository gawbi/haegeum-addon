# 실시간 추론 성능 벤치마크 (CPU)

`benchmarks/latency_benchmark.py` 를 실행해 얻은 **실측값**입니다. 추정치·이론치는 없습니다.
원시 수치는 [`results.json`](results.json) 에 그대로 저장됩니다.

```bash
make benchmark        # = python benchmarks/latency_benchmark.py --iters 2000 --warmup 300 --threads 1
```

## 왜 측정하는가

기존 실험(`advanced_attacks.py`, 노트북)은 전부 오프라인 배치 평가라 "탐지가 되는가"만
답할 수 있었습니다. 온보드 L1 방어 모듈은 **센서 발행 주기 안에** 판단을 끝내야 의미가
있으므로, 단일 윈도우 추론 지연시간을 센서 주기와 직접 비교했습니다.

## 측정 환경 (results.json `meta.environment`)

| 항목 | 값 |
|---|---|
| 칩셋 | Apple M5 (10코어) |
| OS | macOS 26.4 (arm64) |
| Python | 3.14.3 |
| PyTorch | 2.11.0 (CPU, CUDA 미사용) |
| `torch.set_num_threads()` | **1** (온보드 단일 추론 스레드 가정) |
| 양자화 백엔드 | qnnpack (`torch.backends.quantized.engine`) |
| 반복 | 워밍업 300회 + 측정 2,000회 (설정별 개별 `perf_counter` 측정) |
| 시드 | 42 (`utils/seed.py`) |

측정 대상은 `anomaly_detector.py` 의 `VAE` 클래스와 기존 가중치(`vae_uav.pth`,
`vae_ugv.pth`)를 그대로 로드한 것입니다(`utils/load_model.py`). 모델 구조를 새로
정의하지 않았고, 1회 측정 구간은 `AnomalyDetector._infer()` 와 동일하게
**VAE forward + 재구성 MSE 계산**까지 포함합니다.

때문에 **꼬리 지연(p99)만 나빠집니다**. 온보드에서는 스레드 1개로 고정하는 편이 지연
예측 가능성 측면에서 유리하다는 실측 근거입니다.

## 2) 실시간성 판단 — 센서 발행 주기 대비

`sensor_publisher.py` 의 발행 주기 파라미터는 `rate_hz` 기본값 **10.0 Hz** 이고
(`self.create_timer(1.0 / rate, self.publish_sensor)`), 윈도우가 한 칸 밀릴 때마다
추론 1회가 필요하므로 **샘플당 예산 = 100 ms** 입니다.

| 플랫폼 | 센서 주기 | p99 지연 (FP32) | 예산 사용률 | 여유 | 이론상 지속 가능 최대 주기 |
|---|---|---|---|---|---|
| UAV | 100 ms | 0.119 ms | **0.12 %** | 839× | 8,393 Hz |
| UGV | 100 ms | 0.041 ms | **0.04 %** | 2,431× | 24,313 Hz |

**판단: 실시간 처리 가능.** 10 Hz 센서 스트림에 대해 최악(p99)에서도 주기의 0.12 % 만
사용하며, 단일 CPU 스레드로 UAV·UGV 양쪽을 동시에 돌려도 여유가 3자리수 배입니다.
`AnomalyDetector` 의 나머지 경로(정규화, 임계값 비교, 이벤트 직렬화)는 NumPy 연산 몇 줄
수준이라 이 예산을 잠식하지 않습니다. 다만 아래 한계를 함께 봐야 합니다.

- 여기서 말하는 지연은 **추론 지연**이지 **탐지 지연**이 아닙니다. 슬라이딩 윈도우가
  공격 데이터로 채워지는 데 필요한 시간(최대 20 샘플 = 2 s @10 Hz)과, 점진적 스푸핑에서
  관측된 탐지 지연(최대 500 ms, 저장소 루트 README 참조)이 실제 반응 시간을 지배합니다.
- ROS2 미들웨어 전송 지연·DDS QoS 는 이 측정에 포함되지 않았습니다.
- Apple M5 는 실제 온보드 SoC(Jetson Orin Nano, i.MX8 등)보다 빠릅니다. 아래 컨테이너
  실측처럼 환경이 바뀌면 수 배 느려질 수 있으나, 3자리수 배의 여유가 이를 흡수합니다.

## 3) 경량화(동적 양자화, qint8) 비교

`torch.ao.quantization.quantize_dynamic(model, {nn.Linear}, dtype=torch.qint8)` 적용.

### ① 모델 크기

| 플랫폼 | 파라미터 | FP32 state_dict | INT8 state_dict | 감소 |
|---|---|---|---|---|
| UAV | 60,992 | 249,417 B (244 KB) | 72,599 B (71 KB) | **-70.9 %** |
| UGV | 71,272 | 290,505 B (284 KB) | 82,967 B (81 KB) | **-71.4 %** |

### ② 지연시간 — 호스트에서는 **오히려 느려짐**

| 플랫폼 | FP32 p50 | INT8 p50 | 변화 |
|---|---|---|---|
| UAV (batch=1) | 0.032 ms | 0.123 ms | **3.8× 느림** |
| UGV (batch=1) | 0.033 ms | 0.123 ms | **3.7× 느림** |

행렬이 작아(최대 200×128) qnnpack 양자화 커널의 양자화/역양자화 오버헤드가 연산 절감분을
넘어섭니다. 반대로 **Linux 컨테이너(linux/arm64, 동일 스크립트 2,000회 실측)** 에서는
FP32 가 Accelerate BLAS 를 못 쓰기 때문에 INT8 이 더 빨랐습니다.

| 환경 | UAV FP32 p50 | UAV INT8 p50 | UGV FP32 p50 | UGV INT8 p50 |
|---|---|---|---|---|
| 호스트 (macOS, Apple M5) | 0.032 ms | 0.123 ms | 0.033 ms | 0.123 ms |
| Docker (python:3.12-slim, linux/arm64) | 0.163 ms | 0.100 ms | 0.178 ms | 0.114 ms |

컨테이너에서도 p99 는 UAV 1.91 ms / UGV 2.86 ms(FP32)로 센서 주기 예산의 1.9~2.9 % 만
사용해 실시간성 판단은 바뀌지 않습니다(여유 35~52배).

→ **양자화의 이득은 하드웨어/BLAS 백엔드에 따라 부호가 바뀝니다.** 이 규모의 모델에서
양자화를 채택할 근거는 지연시간이 아니라 **메모리/플래시 71 % 절감**이며, 실제 타깃
보드에서 같은 스크립트를 돌려 재확인해야 합니다.

### ③ 탐지 성능 — 사실상 변화 없음

기존 임계값(FP32 정상 데이터 95th percentile)을 그대로 적용했습니다.

| 플랫폼 | 항목 | FP32 | INT8 |
|---|---|---|---|
| UAV | 정상 점수 평균 | 1.0242 | 1.0242 |
| UAV | 정상 점수 p95 (= 임계값) | 1.2301 | 1.2293 |
| UAV | 정상 점수 p99 | 1.3597 | 1.3586 |
| UAV | FP32 임계값에서의 오탐률 | 5.00 % | 5.00 % |
| UGV | 정상 점수 평균 | 0.9975 | 0.9975 |
| UGV | 정상 점수 p95 (= 임계값) | 1.1884 | 1.1884 |
| UGV | FP32 임계값에서의 오탐률 | 5.08 % | 5.08 % |

두 플랫폼 모두 FP32-INT8 점수 계열 **Pearson r = 1.0000**. 재구성 오차 분포가 유지되므로
**임계값 재보정 없이 양자화 모델을 그대로 투입할 수 있습니다.**

F1 재측정 (동일 임계값, 경계 윈도우 제외):

| 플랫폼 | 공격 | FP32 F1 | INT8 F1 | 탐지 지연 |
|---|---|---|---|---|
| UAV | GPS Spoofing | 0.9891 | 0.9891 | 100 ms |
| UAV | Altitude Spoofing | 0.9891 | 0.9891 | 0 ms |
| UAV | Command Injection | 0.9891 | 0.9891 | 0 ms |
| UAV | 복합 GPS+CmdInj | 0.9891 | 0.9891 | 0 ms |
| UAV | 점진적 GPS (rate 0.3) | 0.9891 | 0.9891 | 200 ms |
| UGV | GPS Spoofing | 0.7654 | 0.7654 | — |
| UGV | Wheel Slip | 0.9856 | 0.9856 | — |
| UGV | Command Anomaly | 0.9856 | 0.9856 | — |

- UAV 평가는 `advanced_attacks.py` 의 기존 하네스(`gen_normal` / `atk_*` / `run_experiment`)를
  그대로 재사용했습니다. 루트 README 표와 임계값·FP 수가 근소하게 다른 이유는 VAE 가
  재파라미터화 샘플링을 쓰기 때문이며(임계값 1.2283 → 1.2301), 본 스크립트는 시드 42 로
  고정해 재현 가능합니다.
- UGV GPS Spoofing 의 Precision 이 낮은 것(0.62)은 공격이 **50 샘플짜리 순간 버스트**라
  양성 윈도우가 31개뿐이기 때문입니다(오탐 19건 / 음성 912건 = 2.1 %). 재현율은 1.0.
- UGV 평가 데이터는 `utils/ugv_data.py` 로 노트북 생성기를 옮기면서 **정상/공격 시계열
  길이를 n=1000 으로 통일**했습니다. 노트북은 정상 n=1000, 공격 n=300 을 섞어 썼는데
  `generate_normal` 이 `t=linspace(0,10,n)` 의 gradient 로 속도를 만들어, n 이 다르면
  속도 스케일 자체가 달라져 정규화 기준이 어긋납니다(이 상태에서는 공격과 무관한 구간도
  전부 이상으로 잡힘). 자세한 영향은 `explainability/README.md` 참조.

## 재현

```bash
make setup && make benchmark          # 호스트
make docker-build && make docker-run  # 컨테이너
```

지연시간은 머신·부하에 따라 달라지므로, 다른 하드웨어에서 재실행하면 `results.json` 의
`meta.environment` 와 함께 수치를 다시 읽어야 합니다.
